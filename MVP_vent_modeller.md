# MVP: Веб-моделлер вентиляции на That Open Engine

> **Назначение документа.** Единый источник правды для людей (команда, практиканты СПбГАСУ) и для ИИ-агентов (Claude, Qwen, Cursor/Cline). Документ описывает *что строим*, *в каком порядке* и *по каким правилам*. ИИ-агент может брать любую задачу из раздела «Бэклог» и реализовывать её, не выходя за рамки «Архитектуры» и «Контрактов данных».

---

## 0. Резюме в одном абзаце

Веб-приложение, в котором инженер рисует систему вентиляции прямо в 3D-сцене браузера (прямые воздуховоды, отводы/тройники/переходы, решётки/диффузоры, вентустановки), используя сортамент по ВСН 353-86 / ДКС. На выходе — автоматическая ведомость: длины и диаметры воздуховодов, площадь поверхности (м²), спецификация фасонных частей, экспорт в Excel и IFC. Геометрию строит ядро That Open (web-ifc + Clay), данные хранятся на бэкенде с БД.

## 1. Границы MVP (scope)

### Что ВХОДИТ в MVP

| # | Возможность | Приоритет |
|---|-------------|-----------|
| F1 | 3D-сцена с навигацией (орбита, пан, зум) | must |
| F2 | Рисование прямого воздуховода в 3D (точка→точка) | must |
| F3 | Сортамент сечений: круглые + прямоугольные (ВСН 353-86 / ДКС) | must |
| F4 | Автогенерация фасонных в узлах: отвод, тройник, переход | must |
| F5 | Размещение решёток/диффузоров на воздуховоде | must |
| F6 | Размещение вентустановки (как параметрический блок) | should |
| F7 | Расчёт: длины, диаметры, площадь поверхности (м²) | must |
| F8 | Спецификация фасонных частей | must |
| F9 | Экспорт ведомости в Excel (.xlsx) | must |
| F10 | Экспорт модели в IFC | should |
| F11 | Сохранение/загрузка проекта (бэкенд + БД) | must |

### Что НЕ входит в MVP (явно режем)

- Гидравлический/аэродинамический расчёт (потери давления, подбор сечения по расходу) — фаза 2.
- 2D-планы и DWG-подложка — фаза 2.
- Нормоконтроль / RAG по нормам — фаза 3 (стыкуется отдельно, см. §9).
- Коллизии, пересечения с другими разделами (АР/КР) — фаза 3.
- Многопользовательское редактирование в реальном времени — фаза 3.
- Изоляция воздуховодов, узлы крепления, опоры —后.

> **Правило MVP.** Если задача не из таблицы «Что входит» — она не делается в MVP. Сначала рабочий цикл «нарисовал → получил ведомость → выгрузил», потом расширение.

## 2. Технологический стек

### Фронтенд (ядро моделлера)

| Слой | Пакет | Зачем |
|------|-------|-------|
| Геометрия IFC | `@thatopen/fragments` + web-ifc (WASM) | чтение/запись IFC на нативной скорости |
| Построение геометрии | `@thatopen/components` + Clay | генерация IFC-элементов из параметров |
| UI-виджеты | `@thatopen/ui` (`bim-*` компоненты) | панели, кнопки, таблицы |
| Рендер | three.js (под капотом That Open) | сцена, камера, материалы |
| Сборка | Vite + TypeScript | dev-сервер, типизация |

### Бэкенд

| Слой | Технология | Зачем |
|------|-----------|-------|
| API | FastAPI (Python) **или** Node/Express | CRUD проектов, экспорт |
| БД проектов | PostgreSQL | проекты, версии, метаданные |
| Граф объектов | JSONB-поле в Postgres (на старте) | хранить модель как структуру |
| Сортамент | таблица в Postgres | ВСН 353-86 / ДКС, детерминированно |
| Файлы (IFC/xlsx) | объектное хранилище (MinIO/S3) или диск | выгрузки |

> **Лицензия.** That Open Engine — MIT. Свободно для коммерческой/проприетарной надстройки. **Не тащить GPL-зависимости** (Bonsai/производные IfcOpenShell в линковке), чтобы не связать руки при будущей монетизации. Решение о коммерциализации можно отложить — MIT этого не требует сейчас.

## 4. Контракты данных (модель = данные)

Это сердце data-driven подхода. Геометрия **порождается** из этих структур ядром, а не рисуется напрямую. ИИ-агент при реализации обязан соблюдать эти схемы.

### 4.1 Элемент: прямой воздуховод (`Duct`)

```json
{
  "id": "duct-0001",
  "type": "duct",
  "shape": "round | rectangular",
  "size": { "d": 200 },                // круглый: d (мм)
  // или для прямоугольного:
  // "size": { "w": 400, "h": 200 },   // ширина x высота (мм)
  "start": [0, 0, 3000],               // мм, координаты оси
  "end":   [5000, 0, 3000],
  "sortamentRef": "VSN353-R-200",      // ключ записи сортамента
  "material": "steel_galv",
  "system": "P1"                       // имя системы (приток/вытяжка)
}
```

### 4.2 Фасонная часть (`Fitting`) — генерируется автоматически в узле

```json
{
  "id": "fit-0007",
  "type": "fitting",
  "kind": "bend | tee | reducer",
  "angle": 90,                         // для bend
  "connects": ["duct-0001", "duct-0002"],
  "node": [5000, 0, 3000],
  "sortamentRef": "VSN353-BEND-200-90"
}
```

### 4.3 Воздухораспределитель (`Terminal`)

```json
{
  "id": "term-0003",
  "type": "terminal",
  "kind": "grille | diffuser",
  "model": "АМН 200x200",
  "host": "duct-0001",
  "position": [2500, 0, 3000]
}
```

### 4.4 Оборудование (`Equipment`)

```json
{
  "id": "eq-0001",
  "type": "equipment",
  "kind": "ahu",
  "model": "ВУ-1",
  "size": { "l": 1200, "w": 600, "h": 600 },
  "position": [0, 0, 3000]
}
```

### 4.5 Проект (корневой объект)

```json
{
  "projectId": "uuid",
  "name": "Кампус — корпус А — П1",
  "version": 3,
  "units": "mm",
  "elements": [ /* Duct | Fitting | Terminal | Equipment */ ]
}
```

> **Принцип.** Модель целиком восстановима из этого JSON: ядро по нему перестроит всю геометрию. Это и есть data-driven моделинг — данные первичны, тело вторично.

## 5. Сортамент (детерминированный слой)

Таблица в Postgres. Размеры **берутся только отсюда**, не вводятся произвольно — это гарантирует соответствие ВСН 353-86 / ДКС и корректную спецификацию.

| поле | пример | описание |
|------|--------|----------|
| `ref` | `VSN353-R-200` | уникальный ключ |
| `shape` | `round` | круглый/прямоугольный |
| `d` / `w`×`h` | 200 | размер, мм |
| `wall_thickness` | 0.5 | толщина стенки, мм |
| `mass_per_m` | 2.4 | масса пог. м, кг (для спецификации) |
| `source` | `ВСН 353-86` | норматив-источник |

> Фасонные части тоже из сортамента: отвод/тройник/переход имеют свои `ref` с привязкой к диаметру и углу.

## 6. Расчётный модуль → ведомость

Обходит граф элементов и собирает:

1. **Длины и диаметры** — суммарная длина по каждому типоразмеру (группировка по `sortamentRef`).
2. **Площадь поверхности (м²)** — для расчёта окраски/изоляции:
   - круглый: `S = π · d · L`
   - прямоугольный: `S = 2·(w + h) · L`
3. **Спецификация фасонных** — подсчёт `Fitting` по `kind` + `sortamentRef`.
4. **Масса** (бонус, если есть `mass_per_m`) — `Σ mass_per_m · L`.

Результат → таблица в UI (`bim-table`) → экспорт.

### Формат ведомости (Excel)

| Поз | Наименование | Тип | Размер | Ед. | Кол-во | S, м² | Масса, кг | Норматив |
|-----|--------------|-----|--------|-----|--------|-------|-----------|----------|
| 1 | Воздуховод круглый | round | ⌀200 | м | 45,0 | 28,3 | 108,0 | ВСН 353-86 |
| 2 | Отвод 90° | bend | ⌀200 | шт | 6 | — | — | ВСН 353-86 |

## 7. Дорожная карта по фазам

### Фаза 0 — Каркас (фундамент)
- Vite + TS + That Open, пустая 3D-сцена с навигацией (F1).
- Бэкенд FastAPI/Node + Postgres, схема `projects` (JSONB).
- Заливка сортамента в БД (§5).
- **Критерий готовности:** сцена крутится, проект сохраняется/грузится пустым.

### Фаза 1 — Рисование воздуховодов
- Инструмент «воздуховод»: клики в 3D → осевая линия → Clay строит тело (F2).
- Выбор сечения из сортамента, круглые + прямоугольные (F3).
- Snapping к сетке и к концам существующих воздуховодов.
- **Критерий:** можно нарисовать связную трассу из нескольких участков.

### Фаза 2 — Узлы и элементы
- Автогенерация фасонных в узлах: отвод/тройник/переход (F4).
- Решётки/диффузоры на воздуховоде (F5).
- Вентустановка как блок (F6).
- **Критерий:** трасса с фасонными и концевыми устройствами выглядит как система.

### Фаза 3 — Ведомость и экспорт
- Расчётный модуль: длины, S, спецификация фасонных (F7, F8).
- Экспорт Excel (F9).
- Экспорт IFC (F10).
- **Критерий:** полный цикл «нарисовал → ведомость → .xlsx + .ifc».

> **Это и есть граница MVP** — конец фазы 3. Всё ниже — потом.

### Пост-MVP (фаза 4+)
- Аэродинамический расчёт, подбор сечения по расходу.
- DWG-подложка, рисование по 2D-плану.
- Нормоконтроль / RAG (§9).
- Коллизии, изоляция, опоры.

## 8. Риски и честные оговорки

| Риск | Суть | Митигация |
|------|------|-----------|
| Объём слоя рисования | «рисовать мышкой в 3D» — самая дорогая часть, snapping и узлы нетривиальны | начать с минимума: точка→точка, без сложного snapping; усложнять итеративно |
| Clay-API зрелость | редактор геометрии That Open моложе вьюера | держать геометрию простой (extrude по оси), сложные фасонные — параметрически |
| Соблазн расширить scope | «давай ещё расчёт/планы» | строго держать §1, всё лишнее → бэклог |
| 3D-черчение vs 2D-привычка инженера | инженерам привычнее план | в MVP принято «сразу 3D», 2D-план — фаза 4 |

> **Реалити-чек.** Веб-моделлер инженерного уровня — это месяцы работы команды, не вечер. MVP здесь — узкий вертикальный срез «вентиляция → ведомость», а не «свой Revit».

## 9. Точка стыковки с нормоконтролем (на будущее)

Data-driven архитектура (§4) уже готова к проверкам: граф элементов → гибридная база норм (vector + структурная БД + rule engine) → замечания с цитатой пункта. В MVP не реализуем, но контракты данных §4 проектируем так, чтобы каждый элемент нёс параметры, достаточные для будущей проверки (сечение, материал, система, привязки). Стыкуется с существующим стеком RAGFlow / Ollama / NotebookLM.

## 10. Инструкция для ИИ-агента

При работе над этим проектом ИИ-агент обязан:

1. **Не выходить за scope §1.** Задача не из таблицы «Что входит» → не делать, предложить в бэклог.
2. **Соблюдать контракты §4.** Любой новый элемент описывается JSON-схемой того же стиля; геометрия порождается из данных, не хардкодится.
3. **Размеры только из сортамента §5.** Никаких произвольных диаметров в коде.
4. **MIT-чистота.** Не добавлять GPL-зависимости.
5. **Геометрия — через Clay/web-ifc.** Не рисовать «голые» three.js-меши в обход IFC-слоя (иначе сломается экспорт IFC).
6. **Каждая фаза §7 заканчивается рабочим циклом**, а не «почти готово». Сначала вертикальный срез, потом ширина.
7. **Перед изменением чужого кода — спросить.** Несанкционированные правки запрещены.
