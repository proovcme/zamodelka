## 1. Видение и сценарий

Инженер пришёл на стройку с ноутбуком/планшетом и за 10–15 минут **быстро накидывает**
то, что видит: **стены**, **кабельные лотки**, **воздуховоды**. Без подготовки, минимум
кликов, привязки делают за него точность. На выходе — 3D‑модель, автоматическая
спецификация по разделам и экспорт (IFC + Excel).

**Ключевые ценности (по приоритету):**
1. **Скорость ввода** — клик‑клик‑клик, цепочки, горячие клавиши, ПКМ‑сброс.
2. **Умные привязки** — к сетке, к узлам, к осям, **по углу с шагом 5°**.
3. **Корректная геометрия** — авто‑фасонные части, без «обратных» углов.
4. **Авто‑спецификация** — считается на лету по мере черчения.
5. **Экспорт** — IFC и Excel‑ведомости.

Антипример (чего НЕ хотим): сложный параметрический редактор с диалогами на каждый шаг.

## 3. Единый «линейный инструмент» (фундамент)

Стены, лотки, воздуховоды чертятся **одинаково**. Нужен общий базовый инструмент
(назовём `BaseLineTool`), от которого наследуются конкретные. Это снимает дублирование
и даёт единое поведение привязок.

**Поведение:**
- Клик 1 — старт; клик 2 — конец участка; далее **цепочка** от последней точки.
- ПКМ — завершить/сбросить (как сейчас, событие `tool-deactivated`).
- Превью‑меш во время движения мыши + индикатор привязки.
- **Динамический ввод (CAD‑style):** у курсора показывать **длину** текущего участка и
  **угол** поворота. Желательно — ввод длины/угла с клавиатуры (Phase 2).
- Глобальные параметры из тулбара: **отметка**, **шаг сетки**, **шаг угла (=5° по умолч.)**.

## 4. Угловая логика (УТОЧНЕНО заказчиком — ключевой пункт)

> Дословно: «обратных углов не бывает», «обычно шаг в 5 градусов».

**FR‑ANG‑1. Привязка направления к шагу 5°.**
Направление чертимого участка привязывается к ближайшему кратному **5°** в горизонтальной
плоскости (XZ). Шаг настраивается в тулбаре (5° по умолчанию; варианты 1°/5°/15°/45°/90°).
Привязка считается относительно мировых осей, а в режиме цепочки — дополнительно
относительно предыдущего сегмента.

**FR‑ANG‑2. Запрет «обратных» углов.**
Участок не может складываться назад. Отклонение направления нового участка от
предыдущего ограничено диапазоном **0°…90°** (поворот «по ходу», не острее прямого угла).
Резкие/обратные складки невозможны: точка отклоняется (визуальный фидбэк + событие
`segment-angle-rejected`). Развороты делаются ДВУМЯ участками по ≤90°, а не одной острой
складкой.

**FR‑ANG‑3. Подсказка угла.**
Во время черчения у курсора отображается текущий угол (кратный 5°) и длина. При
запрещённом угле — превью красное/перечёркнутое.

**FR‑ANG‑4. Связь с фасонными частями.**
Фактический угол участка определяет фасонную часть (отвод 90/45/30/15° и т.п.). Генератор
получает угол уже дискретизированным (кратным 5°), что упрощает подбор стандартных деталей.

> В текущем коде `DuctDrawingTool` уже есть запрет dot<0 (FR‑ANG‑2 частично). Нужно:
> вынести логику в `BaseLineTool` и добавить **дискретизацию 5°** (FR‑ANG‑1).

## 5. Новые сущности графа

Расширяем плоский массив `projectElements`. Координаты — **мм**, `[x, y, z]`, Y — вверх.

### 5.1 Стена — `type: "wall"`
```ts
{
  id: "wall-<ts>-<rnd>",
  type: "wall",
  start: [x, y, z],     // мм, осевая линия (Y = отметка низа стены / пола)
  end:   [x, y, z],
  height: 3000,         // мм
  thickness: 200,       // мм
  material?: "brick" | "concrete" | "gypsum" | string,
  baseOffset?: 0        // мм, смещение низа от отметки (опц.)
}
```
- **Привязки:** орто + 5°, к концам/осям других стен. Угловые соединения (L/T/X) —
  упрощённо: стыковка по осевым линиям (без булевых вырезов в Phase 1).
- **3D:** вытянутая коробка по оси, высотой `height` вверх от Y.
- **Спецификация:** длина (м), площадь поверхности (м²), объём (м³).

### 5.2 Кабельный лоток — `type: "tray"`
```ts
{
  id: "tray-<ts>-<rnd>",
  type: "tray",
  start: [x, y, z],
  end:   [x, y, z],
  width: 200,           // мм
  height: 80,           // мм (высота борта)
  kind: "ladder" | "perforated" | "solid",  // лестничный/перфорированный/сплошной
  system?: string,      // напр. "Силовые", "Слаботочка"
  sortamentRef?: string
}
```
- **Фасонные части лотка** (аналог `FittingGenerator`): повороты (90/45°, горизонт. и
  вертикальные), тройники, крестовины, переходы по ширине. Phase 1 — хотя бы повороты и
  тройники.
- **3D:** U‑образный профиль (дно + два борта) по оси; для `ladder` — упрощённо короб с
  прорезями или просто короб с маркировкой типа.
- **Спецификация:** длина (м), кол‑во фасонных (шт), аксессуары.

### 5.3 Воздуховод — `type: "duct"` (уже есть)
- Доработать: угловая привязка 5° (FR‑ANG), общий `BaseLineTool`.

## 6. Функциональные требования (нарезка задач)

**Фундамент**
- **FR‑1.** Вынести привязки (сетка/узлы/оси/угол) в общий модуль `Snapping`,
  используемый всеми линейными инструментами. Параметры: шаг сетки, шаг угла, пороги.
- **FR‑2.** `BaseLineTool` — общий жизненный цикл линейного черчения (цепочка, превью,
  ПКМ‑сброс, динамические подсказки длины/угла). `DuctDrawingTool` переводится на него
  без регрессий.
- **FR‑3.** Реализовать FR‑ANG‑1…4 (шаг 5°, запрет обратных, подсказка, дискретный угол).

**Стены**
- **FR‑4.** Инструмент «Стена» (черчение цепочкой, параметры height/thickness/material).
- **FR‑5.** 3D‑отрисовка стен в `renderAll` (короб по оси, высота вверх от отметки).
- **FR‑6.** Стыковка стен в углах/Т‑узлах (упрощённо, без булевых операций в Phase 1).
- **FR‑7.** Свойства стены в панели + раздел «Стены» в спецификации (длина/площадь/объём).

**Лотки**
- **FR‑8.** Инструмент «Лоток» (цепочка, параметры width/height/kind/system).
- **FR‑9.** 3D‑отрисовка лотков (U‑профиль) в `renderAll`.
- **FR‑10.** Генератор фасонных частей лотков (повороты, тройники, переходы) — обобщить
  `FittingGenerator` либо отдельный модуль с тем же подходом (группировка узлов).
- **FR‑11.** Свойства лотка + раздел «Лотки» в спецификации.

**Общее / интеграция**
- **FR‑12.** Тулбар: переключатель активного типа (Стена / Лоток / Воздуховод), их
  параметры, глобальные поля «Отметка», «Шаг сетки», «Шаг угла».
- **FR‑13.** Расширить `BOMCalculator` и панель спецификации новыми разделами; сохранить
  читаемость (контраст!) и строки «Итого».
- **FR‑14.** Бэкенд: добавить сортамент лотков (типоразмеры, масса/м), расширить
  Excel‑экспорт разделами «Стены»/«Лотки».
- **FR‑15.** IFC‑экспорт: воздуховод → `IfcDuctSegment`, лоток → `IfcCableCarrierSegment`,
  стена → `IfcWallStandardCase` (хотя бы как параметрические тела/прокси).

## 10. Критерии приёмки (примеры, расширить под каждую FR)

- **Углы:** при черчении направление прилипает к 5°; попытка сделать острый/обратный
  угол отклоняется, превью краснеет; разворот собирается двумя участками.
- **Стена:** начерченная цепочка стен корректно стоит в 3D (высота, толщина), в
  спецификации есть длина/площадь/объём, свойства открываются по клику.
- **Лоток:** на повороте появляется фасонная часть; ширина/тип отражаются в 3D и спеке.
- **Без регрессий:** воздуховоды, отводы, переход прямоугольник→круг, спецификация и
  экспорт продолжают работать как раньше.
- **Качество (обязательно для приёмки):** `npx tsc --noEmit` чисто, `npm run build`
  собирается, **проверено в браузере** (поднят бэкенд + фронт, начерчено вручную).

## 13. Известные дефекты (обязательно починить)

### 🔴 BUG‑IFC‑1. Загрузка IFC молча зависает (ни у кого не работает)
**Симптом:** кнопка «IFC» в панели моделей → выбираешь файл → **вечный спиннер,
никакой ошибки в консоли**, вкладка может повиснуть. Не работает ни у кого.

**Диагностика (проверено в браузере):**
- Сам `web-ifc.wasm` (0.0.72, однопоточный) исправен: компилируется в браузере за ~4 мс,
  SharedArrayBuffer / cross‑origin isolation ему **НЕ нужны** (это не причина).
- Прямой вызов `ifcLoader.load(bytes, …)` зависает >30 c без ошибок.

**Корень:** WASM грузится из интернета в рантайме —
```ts
// src/main.ts
await ifcLoader.setup({
  autoSetWasm: false,
  wasm: { absolute: true, path: "https://unpkg.com/web-ifc@0.0.72/" }, // ← внешний CDN
});
```
На целевых сетях (VPS в РФ, корпоративный фаервол, **офлайн на стройке**) запрос к
`unpkg.com` за ~1.3 МБ блокируется/висит → `load()` зависает навсегда. Локальная копия
wasm **есть** в `node_modules/web-ifc/`, но папки `public/` нет и она не раздаётся.
Усугубляется тем, что загрузка в `sections/models.ts` (`onAddIfcModel`) сделана **без
try/catch и без таймаута** → любой сбой = молчаливый вечный спиннер.

**Что сделать (FR‑IFC‑1):**
1. **Вендорить WASM локально:** положить `web-ifc.wasm`, `web-ifc-mt.wasm`
   (и при необходимости `web-ifc-node.wasm`) из `node_modules/web-ifc/` в `public/web-ifc/`
   (можно скриптом в `postinstall`/`predev`, чтобы не коммитить бинарь руками), и поменять
   на `wasm: { absolute: false, path: "/web-ifc/" }`. Убрать зависимость от unpkg.
2. **Обработка ошибок и фидбэк:** в `onAddIfcModel` обернуть `load()` в try/catch,
   показывать пользователю ошибку (а не молчать), сбрасывать `target.loading` в `finally`,
   опционально — таймаут с понятным сообщением.
3. **Проверить путь воркера/ассетов** при `vite.config base: "./"`: на VPS под суб‑путём
   относительные URL воркера фрагментов и wasm могут поехать. Локальный `/web-ifc/`
   (absolute от корня) надёжнее; worker подключается через `?url` (Vite) — убедиться, что
   в проде (`npm run build`) он реально доступен.

**Критерий приёмки:** при **полностью отключённом интернете** (DevTools → Network →
Offline) выбор валидного `.ifc` приводит к загрузке и отображению модели в сцене;
при битом файле — видимая ошибка, спиннер гаснет. Проверено в браузере, не только в коде.

### Прочие известные (контекст, не из этого ТЗ — но мешают финалу)
- **Сборка `npm run build` не проходит** (~15 ошибок TS6133 «unused» в `viewer-toolbar.ts`)
  — следствие незаконченного рефакторинга тулбара. Деплой из текущего HEAD не соберётся,
  пока не дочищено. На `vite dev` (esbuild) не мешает.
- **Из тулбара пропали контролы параметров** (форма/типоразмер/отметка/шаг угла/параметры
  стен‑лотков‑труб): в разметке 0 `bim-dropdown`/`bim-number-input`, отсюда и
  «неиспользуемые» обработчики. Параметры задаются только дефолтами + подхватом при клике
  по существующему элементу. Вернуть контролы в тулбар (или осознанно перенести в панель).

## 14. Работа с загруженным IFC (подложка / контекст)

**Концепция:** загруженный IFC — это **read‑only контекст** (съёмка существующего здания),
по которому проектировщик ориентируется и **чертит поверх свои элементы**
(воздуховоды/стены/лотки). IFC в этом движке — запечённая для просмотра геометрия
(fragments), а не редактируемая параметрическая модель, поэтому редактором чужого IFC
приложение НЕ становится.

## 17. Рабочая плоскость на отметке (видимая сетка едет за высотой)

### FR-GRID-1. Видимая сетка синхронно с текущей отметкой  ·  сложность: 🟢 низкая

**Текущее состояние:** плоскость привязки уже двигается на `currentElevation`

(в `main.ts`) прибита к Y=0 и не двигается. Нужно их синхронизировать.

**Что сделать:**
1. При смене отметки (`currentElevation` / событие `elevation-updated`) сдвигать визуальную
   сетку по Y на ту же отметку. Реализация зависит от того, как `OBC.Grids` позволяет
   смещать сетку: либо двигать объект сетки по Y, либо параметром плоскости. Если штатно
   не двигается — допускается своя плоскость-сетка (`THREE.GridHelper`/шейдер) на высоте
   отметки.
2. Лёгкая подпись текущей отметки у сетки/в углу вьюпорта (напр. «+3.000»), чтобы высота
   читалась.

## 18. Измерения «Длина» и «Площадь» — починить (сейчас «для красоты»)

### FR-MEASURE-1. Рабочие инструменты измерения  ·  ✅ ПОЧИНЕНО (корень найден)
**Итог фикса:** причина была в `rebuildWorldMeshes` (`main.ts`) — в `world.meshes` клались
меши IFC-фрагментов с GPU-геометрией (без `position.array`), и OBC-рейкастер измерителя/
клиппера падал на них на каждом pointermove → Length/Area/Clipper не создавали ничего при
загруженном IFC. Исправлено фильтром по `position.array`. Проверено в браузере: Length и
Clipper создают результат (`list.size > 0`, без ошибок) при загруженной IFC-модели. Подробно —
`VENT_MVP_SKILL.md` §11.2 и §17 п.11. Измерение по самим воздуховодам/стенам работает; по IFC —
не снапится (фрагменты стандартным raycast не берутся), это осознанное ограничение.

<details><summary>Исходный диагноз (история)</summary>
**Симптом:** кнопки «Measurements → Length / Area» есть, но замер **не создаётся вообще**.

**Статус (проверено в браузере, не по коду):** предыдущая итерация уже переключила вызов на
`pointerdown` с гейтом по `.enabled` (длина/площадь/clipper зовут `create()` только когда
включены) — это правильно и сделано. **НО по факту замер не появляется:** при включённом
`LengthMeasurement`/`AreaMeasurement` и кликах по `bim-viewport` список замеров
(`measurer.list`) остаётся **пустым (0)**. То есть «реализовано и проверено» из отчёта —
неверно, ни одной линии/площади не создаётся.

**Где собака зарыта (гипотеза для проверки):** OBF-инструменты
`LengthMeasurement`/`AreaMeasurement` ведут СВОЁ отслеживание курсора и рейкастят по
геометрии под мышкой. Ручной `create()` из нашего `pointerdown` срабатывает «вхолостую»,
если у инструмента нет валидной точки наведения (или если он сам уже слушает события и
происходит конфликт/двойная обработка). Нужно:
1. Свериться с актуальным API OBF для 3.2.x: как именно эти инструменты ожидают создание
   замера — через свой внутренний обработчик (просто `.enabled = true` + клики), или через
   ручной `create()` на даблклик, и нужна ли точка под курсором (по геометрии).
2. Возможно, НЕ звать `create()` вручную, а дать включённому инструменту обрабатывать клики
   самому; либо наоборот — звать `create()` только при наличии валидного hit (как у нас в
   `Snapping.getIfcIntersection`/рабочей плоскости).
3. Убедиться, что наш `pointerdown`-выбор и инструменты черчения не съедают клики измерителя.

**Сечение (Clipper):** та же природа — требует геометрии под курсором; проверить тем же
сценарием (клик по IFC/воздуховоду ставит плоскость реза).

**Приёмка (жёстко, только глазами в браузере):** включаю Length → два клика по
воздуховоду/IFC → **в сцене видна линия с числом длины**; Area → виден замкнутый контур с
площадью; Section → виден рез модели. Проверять по `measurer.list.size > 0` и визуально, а
НЕ по тому, что «код выглядит правильно». Отчёт без скриншота/видео реального замера не
принимается.
</details>

**Остаётся (Area):** Length и Clipper проверены и работают; Area по той же механике должна
работать — подтвердить замкнутый контур с площадью в браузере.
