# vent_mvp — руководство для ИИ (и людей)

> Это **единый источник правды** по проекту. Проект небольшой, но плотный: данные в
> миллиметрах, сцена в метрах, UI на веб-компонентах с неинтуитивным жизненным циклом.
> Большинство ошибок здесь — не «логика не та», а «не знал про конвенцию/грабли».
> Читай до конца, потом меняй код. Любой вывод проверяй в браузере (см. §16).

## 1. Что это за проект

**Vent MVP** — браузерный 3D‑моделлер систем вентиляции (домен ОВиК / HVAC).
Пользователь чертит трассы воздуховодов мышью на плоскости, система автоматически
вставляет фасонные части (отводы, тройники, переходы), считает спецификацию
(ведомость материалов) и умеет выгружать Excel‑ведомость и IFC‑модель.

- **Фронтенд:** That Open Engine (`@thatopen/*` ~3.2.0) поверх Three.js 0.175.0,
  UI на `@thatopen/ui` (веб‑компоненты `bim-*`), сборка Vite, язык TypeScript.
- **Бэкенд:** FastAPI + SQLAlchemy + SQLite (`vent_mvp.db`). Хранит проекты (граф
  элементов в JSON) и справочник сортамента воздуховодов (ВСН 353‑86).
- **UI и комментарии — на русском.** Идентификаторы кода — на английском. Сохраняй
  этот стиль.

## 3. Как запустить и как проверять

### Бэкенд (порт 8000)
Запускать **из корня репозитория как модуль** (в `server/main.py` относительные
импорты `from .database ...`, поэтому `python main.py` из папки server упадёт):
```bash
source server/.venv/bin/activate
python3 -m server.main          # uvicorn на 127.0.0.1:8000, reload=True
```
При первом старте создаётся `vent_mvp.db` и наполняется сортаментом.

### Фронтенд (порт 5173, если занят — следующий свободный)
```bash
npm run dev        # vite --host
```
⚠️ Нужен **настоящий node** (nvm/homebrew). На Mac mini node не в PATH у не-логин SSH —
запускай из логин-окружения. НЕ через «electron-as-node» (node от VS Code/Antigravity):
vite падает на нативном `@rollup/rollup-darwin-arm64` (`ERR_DLOPEN_FAILED`, разные Team ID
подписи — Electron не грузит чужой `.node`). tsc им гонять можно, vite — нет.

### Проверка изменений
- `npx tsc --noEmit` — типы (быстро, обязательно).
- `npm run build` — полная сборка (`tsc && vite build`). Предупреждение про размер
  чанка >500 кБ — это норма для That Open, игнорируй.
- **Живая проверка в браузере** — единственный надёжный способ для UI/3D. В репо есть
  `.claude/launch.json` (конфиг `vent-frontend`, порт 5173) для preview‑инструмента.
  Бэкенд должен быть поднят отдельно (preview его не запускает).

## 5. Модель данных — граф элементов (ГЛАВНОЕ)

Вся «модель» — это **один плоский массив** `projectElements: any[]`. Он создаётся
в `main.ts` ОДИН раз и **по ссылке** передаётся всем трём инструментам через
`setElements(projectElements, callback)`. То есть все инструменты пишут в один и тот же
массив — это единый источник правды. Бэкенд хранит его как `graph.elements`.

Каждый элемент — объект с полем `type`. Координаты **всегда в миллиметрах**, массивом
`[x, y, z]`, где **Y — вертикаль (отметка)**.

### 5.1 Воздуховод — `type: "duct"`
```ts
{
  id: "duct-<ts>-<rnd>",
  type: "duct",
  shape: "round" | "rectangular",
  size: { d?: number } | { w: number, h: number },   // мм; d для круглых, w×h для прямоугольных
  start: [x, y, z],   // мм
  end:   [x, y, z],   // мм
  sortamentRef: "VSN353-R-200",
  material: "steel_galv",
  system: "P1"
}
```

### 5.2 Фасонная часть — `type: "fitting"` (генерируется автоматически!)
```ts
{
  id: "fit-<kind>-<ts>-<rnd>",
  type: "fitting",
  kind: "bend" | "tee" | "reducer",   // отвод | тройник | переход
  angle?: number,                     // для отвода, градусы
  connects: string[],                 // id воздуховодов, сходящихся в узле
  node: [x, y, z],                    // мм, точка узла
  sortamentRef: string,
  size?: { d? } | { w?, h? }
}
```
Фасонные части **не создаются руками** — их пересоздаёт `FittingGenerator` (см. §12)
при каждом сохранении воздуховода.

### 5.3 Оконечное устройство — `type: "terminal"`
```ts
{
  id: "term-<ts>-<rnd>",
  type: "terminal",
  kind: "grille" | "diffuser",   // решётка | диффузор
  model: "Решётка АМН 300x200",
  host: "<duct id>",             // воздуховод, на котором сидит
  position: [x, y, z]            // мм, точка на поверхности воздуховода
}
```

### 5.4 Оборудование — `type: "equipment"`
```ts
{
  id: "eq-<ts>-<rnd>",
  type: "equipment",
  kind: "ahu",
  model: "Вентустановка ВУ-1",
  size: { l: 1200, w: 600, h: 600 },  // мм
  position: [x, y, z],                // мм, ЦЕНТР блока
  rotation: number                    // градусы (поворот вокруг Y)
}
```

### 5.5 Расширенные типы (добавляются по ТЗ — см. TZ_FIELD_SKETCH.md)
Граф расширяется новыми `type` по мере реализации полевого эскиза. Уже встречаются в коде:
`"wall"` (стена: `start/end`, `height`, `thickness`, `material`),
`"tray"` (кабельный лоток: `start/end`, `width`, `height`, `kind`),
`"pipe"` (труба), а также электрика `"socket"`/`"panel"`/`"light"`.
**Правила те же:** координаты в мм, Y — отметка, у меша `userData.elementId`, новые типы
надо завести в `renderAll` (отрисовка), `elements-data.ts` (свойства),
`BOMCalculator`/`specification.ts` (спецификация) и при необходимости в `FittingGenerator`.

### 5.6 Системы (SystemManager) — авто-формирование по связности
Над `system` (строка-медиум: «Подача»/«Обратка»/«Приточный») есть НАДстройка — **система-
экземпляр** (ОВ1, ОВ2…), поле `systemId` у элементов. Считает `bim-components/SystemManager`:
- **Связность** (union-find): элементы в одной системе, если делят координаты (концы труб ↔
  порты приборов ↔ узлы фитингов; округление 10 мм) ИЛИ через явные связи (`fitting.connects`,
  `host` у `terminal`/`*_accessory`). Порты приборов — таблица `PORT_LOCALS` (синхрон с
  `TwoPipeDrawingTool.getEquipmentPorts`).
- **Правило:** компонент = система ТОЛЬКО если есть И трасса (`pipe`/`duct`/`tray`), И прибор
  (`radiator`/`ac`/`ac_ceiling`/`equipment`/`terminal`). Иначе `systemId` не ставится.
- **Нумерация:** отопление+вентиляция+кондиционирование = единый раздел, префикс **«ОВ»**,
  СКВОЗНОЙ счётчик (ОВ1, ОВ2, ОВ3…), по порядку (стабильная сортировка по min id). Электрика
  (лотки) → «ЭО», прочее → «С». Тип (heating/ventilation/conditioning) — для подписи, не префикса.
  ⚠️ Докстринг в `SystemManager/index.ts` (стр.6-7) ВРЁТ — пишет «ХС1/П1/В1», но реальный
  `detectType` выдаёт ОВ/ЭО/С. Верь коду, а не комментарию.
- **Где живёт:** `SystemManager.rebuild(projectElements)` вызывается в `main.ts` на
  `elements-updated`, кладёт реестр в `window.__projectSystems`, шлёт `systems-updated`.
  Вкладка «Системы» (`sections/systems.ts`, нижний блок) читает реестр; ручные имена —
  `window.__systemCustomNames[systemId]`.
- **TODO (в ТЗ §20):** FR-SYS-3 схема-аксонометрия (кнопка «Схема» шлёт `system-isolate`,
  обработчика пока нет), FR-SYS-4 полировка флоу подключения.

### 5.7 Flow-движок (дисциплины декларативно)
Flow-mode по дисциплинам (architecture/ventilation/heating/plumbing/electrical) рендерится из
ОДНОГО декларативного реестра **`flowDisciplines`** в `viewer-toolbar.ts` — НЕ из `if(discipline)`.
```ts
const flowDisciplines: FlowDisciplineDef[] = [
  { id, icon, title, actions: [{ icon, label, active, onClick }, …] }, …
];
// rootDock = flowDisciplines.map(disciplineButton)
// renderActions() = flowDisciplines.find(active).actions.map(actionButton)
```
**Добавить дисциплину или инструмент = одна запись в массиве.** Никаких ветвлений по коду.
Состояние: `window.__flowMode = {activeDiscipline, drawerOpen}`, события `flow-discipline-enter/exit`,
`flow-state-changed`.

### 5.8 Движок узлов подключения (ConnectionNodes) — единая логика
Единая точка `ConnectionNodes.connect(elements, device, target)` — диспетчер по `device.type`.
Новый типовой узел = один `case` + builder, БЕЗ правок вызывающего кода (`main.ts` зовёт `connect`).
- **2-портовые приборы** (`radiator`/`ac`/`ac_ceiling`/`equipment`) → ОДИН builder
  `connectDeviceToPipePair`: режет пару труб магистрали в точках врезки (настоящие T-узлы для
  `FittingGenerator`) + строит подводки к портам. Порты — таблица `DEVICE_PORTS` (синхрон с
  SystemManager). `connectRadiatorLower` — тонкий wrapper (совместимость).
- **`terminal` (диффузор/решётка) → воздуховод** → `connectTerminalToDuct`: режет воздуховод +
  **гибкий флекс ≤ 500 мм** (round `kind:"flex"`) к прибору.
- **`socket` (розетка) → `panel` (щит)** → `connectSocketToPanel`: кабель идёт **ПО ЛОТКАМ**, не
  напрямую. Граф лотков (`buildTrayGraph`, сварка концов по сетке 10 мм) + **Дейкстра** →
  полилиния `socket → вход → [лотки] → выход → щит`. Элемент `{type:"cable", points:[…]}`
  рендерится тонкой трубой (янтарь) в `DuctDrawingTool.renderAll`. Нет/несвязные лотки → fallback
  прямой кабель. Геометрию маршрута подтверждать ВИЗУАЛЬНО.
- Принцип заказчика: фикс-библиотека узлов с ОГРАНИЧЕННЫМИ параметрами, БЕЗ генерации на лету;
  цель подключения — куда УКАЗАЛ пользователь (как у диффузоров), а не авто-поиск.
#### 5.8.1 ConnectFlow — UI-стейт подключения
`ConnectionNodes` (§5.8) — математика узла. Пользовательский сценарий «выбери прибор → выбери цель
→ подключил → снова выбери прибор» вынесен в единый `ConnectFlow` (`src/bim-components/ConnectFlow.ts`).
В `main.ts` сейчас заведены конфиги для `radiator`, `terminal` и `ac`.

**Двухфазный жизненный цикл:**
1. Событие `X-connect-toggle/start` активирует flow, подсвечивает подходящие приборы и показывает
   tooltip рядом с курсором.
2. Первый клик выбирает прибор; flow гасит подсветку приборов и подсвечивает совместимые цели.
3. Второй клик выбирает трассу/цель; вызывается `ConnectionNodes.connect(projectElements, device, target)`.
4. После удачного узла порядок обязателен: `FittingGenerator.generateFittings` →
   `ductDrawingTool.renderAll` → `elements-updated` → `rearm()`.
5. `Esc`, повторный toggle или смена инструмента отменяют flow.

**Добавить новый connect-сценарий** = добавить builder/case в `ConnectionNodes.connect` и один конфиг
`ConnectFlow`. Не копировать старые ручные state-machine блоки.

### 5.9 Движок листов ГОСТ (`ui-templates/sheets/`)
Отдельный движок: `getGostSheetLayout(format, standard, orientation)` + `renderGostSheetSvg(opts)`.
Форматы A4/A3/A2/A1/A0, ориентация `landscape`/`portrait` (A4 по умолчанию книжно), штампы
СПДС(форма 3)/ЕСКД(форма 1). Схема системы (аксонометрия) рендерится в `systems.ts` через
**фронтальную изометрию (ГОСТ 2.317)**: длина X — горизонтально, высота Y — вертикально,
глубина Z — под 45°. «Кидать новые шаблоны схем» = добавлять рендереры контента в этот движок.

### 5.10 Отметки/уровни размещения (currentElevation)
Глобальная отметка черчения/размещения — `currentElevation` (мм) в `viewer-toolbar.ts`.
`applyElevationToTools()` (~стр.702) рассылает `setElevation(currentElevation)` ВСЕМ инструментам
(`duct/wall/equipment/tray/pipe/electrical/terminal/accessory/twoPipe`). Уровни —
`window.projectLevels` (map имя→мм); смена уровня/отметки = событие `elevation-updated`
(`{detail:{elevation}}`). Инструмент размещения строит плоскость по `this.elevation` (пример —
`TerminalPlacementTool`, плоскость `y = elevation/1000`). Нижняя секция flow-панели показывает
контролы уровня/отметки для активных placement-инструментов.

## 6. Система координат и единицы — НЕ ПЕРЕПУТАЙ

- **Данные (граф, бэкенд): миллиметры.** Массивы `[x, y, z]` в мм.
- **Сцена Three.js: метры.** Перевод — деление/умножение на 1000.
  - данные → сцена: `new THREE.Vector3(p[0]/1000, p[1]/1000, p[2]/1000)`
  - сцена → данные: `[v.x*1000, v.y*1000, v.z*1000]`
- **Y — вертикаль (высота / «отметка»).** Плоскость черчения горизонтальна (XZ).
- **Сетка/привязка:** шаг сетки 100 мм = `0.1` м. Привязка к существующим узлам —
  порог 250 мм = `0.25` м (см. `applySnapping`).
- Плоскость черчения поднимается на текущую отметку через
  `mousePlane.constant = -elevationMm/1000` (нормаль `(0,1,0)`).

Если видишь «модель улетела в космос» или «всё крошечное» — почти всегда это
перепутанные мм/метры (лишнее или недостающее /1000).

## 7. Три инструмента черчения

Все три живут в `src/bim-components/*PlacementTool` / `DuctDrawingTool`, создаются в
`main.ts`, кладутся в `window` и управляются из тулбара.

**Общий паттерн:**
- `enabled`, `activate()/deactivate()` — навешивают/снимают слушатели мыши на контейнер
  вьюпорта.
- Делят общий массив `projectElements` (по ссылке).
- `onElementsUpdated()` — колбэк, который шлёт DOM‑событие `elements-updated`.
- **ПКМ (правый клик)** = сброс инструмента: `deactivate()` + событие `tool-deactivated`.
- Только ОДИН инструмент активен одновременно — тулбар вызывает `deactivateAllTools()`
  перед активацией нового.

**Глобалы в `window`** (так инструменты общаются с тулбаром и `main.ts`):
- `window.ductDrawingTool`, `window.terminalPlacementTool`, `window.equipmentPlacementTool`
- `window.selectedCustomElement` — текущий выбранный кастомный элемент (или null)

### 7.1 DuctDrawingTool — самый важный
- Чертит воздуховод по двум кликам, затем **продолжает цепочку** от последней точки.
- `activeParams` — форма, размер, sortamentRef, материал, система, **elevation** (мм).
- `renderAll(elements)` — **полностью перерисовывает ВСЮ сцену** (воздуховоды, фасонные,
  решётки, оборудование) из массива. Это центральный метод отрисовки; вызывается всеми
  инструментами после изменения данных. Он **не генерирует** фасонные части.
- `saveDuct()` (private): добавляет воздуховод → вызывает `FittingGenerator.generateFittings`
  → `renderAll` → `onElementsUpdated()`.
- **Запрет острых/обратных углов:** в `handleMouseDown` хранится `lastSegmentDir`; если
  новый участок поворачивает резче 90° (`lastSegmentDir.dot(newDir) < -1e-3`), точка
  отклоняется и шлётся `duct-angle-rejected`. Допустимы повороты до прямого угла.
- Геометрия фасонных частей строится прямо в `renderAll` через помощники
  `createRoundElbow` (гнутый патрубок — `TubeGeometry` по квадратичной дуге),
  `createRectElbow` (короб по биссектрисе), `createSquareToRound` (лофт «квадрат‑в‑круг»).

### 7.2 TerminalPlacementTool
- Рейкастит **по мешам воздуховодов** (`ductDrawingTool.ductsGroup.children`),
  проецирует точку на ось воздуховода, сажает решётку/диффузор на поверхность
  (смещение по Y на радиус/полувысоту). Отметка наследуется от воздуховода‑хоста.

### 7.3 EquipmentPlacementTool
- Размещение вентустановки на плоскости (с учётом отметки). **Пробел** — поворот на 90°.
- Хранит центр блока: `position.y = отметка + полувысота(300 мм)`.

UI‑панели реактивны через обычные DOM‑события. Запоминай их — это «шина» приложения:

## 9. Выбор кастомных элементов (в `main.ts`)

That Open `Highlighter` подсвечивает только IFC‑модели. Наши воздуховоды — обычные
Three.js меши, поэтому выбор реализован **вручную** в `main.ts`:
- На `pointerdown` по вьюпорту (если не активен инструмент) — рейкаст по `ductsGroup`,
  подсветка меша (`highlightCustomMesh`), запись `window.selectedCustomElement`,
  событие `custom-element-selected`.
- **Тонкость:** при выборе вызывается `highlighter.clear("select")`, что дёргает
  `highlighter.events.select.onClear`. Поэтому в `elements-data.ts` обработчик `onClear`
  **НЕ обнуляет** `selectedCustomElement` — иначе он затёр бы только что выбранный
  элемент. Сброс кастомного выбора делает `clearCustomSelection()` при клике в пустоту.
  Не «чини» это, переставив обнуление обратно — сломаешь свойства.

## 10. FittingGenerator — алгоритм (§12 подробно)

`FittingGenerator.generateFittings(elements)` (чистая функция):
1. Берёт все воздуховоды, группирует их концы по округлённым до 10 мм координатам (узлы).
2. Для каждого узла по числу подходящих воздуховодов:
   - **2 воздуховода под углом** (угол между «исходящими» векторами < 135°) → **отвод (bend)**.
   - **2 воздуховода соосно, но разное сечение/форма** → **переход (reducer)**.
     Разная форма (`round`↔`rectangular`) → переход «прямоугольник‑круг».
   - **3 воздуховода** → **тройник (tee)** (размер по наибольшему).
3. Возвращает `[...ducts, ...trays, ...pipes, ...newFittings, ...others]`, где
   **`others` = ВСЁ остальное** (стены, двери, окна, светильники, щиты, радиаторы, розетки,
   кабели, терминалы, оборудование, рабочие места…) — пробрасывается фильтром
   `type !== duct/tray/pipe/fitting`. Старые автогенерированные фасонные отбрасываются и
   пересоздаются (ручные правки в фитингах исчезнут).
   ⚠️ **КРИТИЧНО (на этом Гемини уронил всё — коммит `4b2acd1`):** `generateFittings` —
   ТОТАЛЬНАЯ функция по типам. Если она забывает пробросить какой-то тип (раньше
   возвращала только `ducts+fittings+terminals+equipment`), то ВСЕ двери/окна/щиты/
   радиаторы/розетки **молча исчезают** при первом же добавлении элемента. Добавил новый
   `type`? Убедись, что он попадает в `others` (он попадёт автоматически, если не
   перечислен в исключениях фильтра) и **проверь, что фильтр исключений не оброс лишним**.

## 11. Привязка и отметка

- `applySnapping(point)`: сначала пытается приклеиться к существующему узлу (порог
  250 мм, возвращает точные координаты узла, сохраняя его Y), иначе округляет X/Z к
  сетке 100 мм и ставит `Y = activeParams.elevation/1000`.
- **Отметка** задаётся глобально в тулбаре (`bim-number-input` «Отметка», шаг 100 мм,
  модульная переменная `currentElevation`). `applyElevationToTools()` пробрасывает её в
  `DuctDrawingTool.setElevation` и `EquipmentPlacementTool.setElevation`, которые двигают
  плоскость черчения. Меняя отметку между участками, получаешь вертикальный стояк.

> Примечание: после рефактора привязки живут в `bim-components/Snapping.ts` +
> `SmartSnap.ts`, а инструменты наследуют `BaseLineTool`. Принципы те же.

### 11.1 ⚠️ Привязка к IFC — по Alt, и НЕ роняй рейкаст fragments (НЕ ОТКАТЫВАТЬ)
Привязка курсора к загруженному IFC (взять точку/отметку с поверхности модели) включается
**ТОЛЬКО при зажатом `Alt`**. Без Alt — свободное черчение по рабочей плоскости, IFC
игнорируется. Гейт стоит в `BaseLineTool` (обработчики move и click):
`const ifcIntersect = event.altKey ? Snapping.getIfcIntersection(...) : null;`

**Почему так (реальный баг, уже чинили — не верни как было):** `Snapping.getIfcIntersection`
раньше вызывался на КАЖДОЕ движение мыши безусловно и **падал** на
`raycaster.intersectObjects(...)` — у fragments-мешей That Open часть мешей без валидного
`geometry.attributes.position`, и стандартный THREE-рейкаст крашится
(`Cannot read properties of undefined (reading '0')`). Хендлер движения падал → точка
черчения замирала при заходе курсора на IFC → ощущалось как **«инструмент упирается в
невидимую границу»**. (Это НЕ был «захват поверхности».)

**Как сделано правильно (сохранять):**
- `getIfcIntersection` фильтрует меши по наличию `geometry.attributes.position` и рейкастит
  **по одному в `try/catch`** (битый меш не роняет весь хендлер), берёт ближайшее.
- Снап к IFC — по `Alt` (по умолчанию свободное черчение приоритетно).
Проверено в браузере: без Alt точка над зданием = рабочая плоскость; с Alt = поверхность IFC;
ошибок нет.

### 11.2 ⚠️ НЕ клади IFC-фрагменты в `world.meshes` (иначе измерения/сечение падают)
`world.meshes` (множество, по которому OBC `SimpleRaycaster` рейкастит для **измерений
(Length/Area) и сечения (Clipper)**) заполняет `rebuildWorldMeshes()` в `main.ts` (по
событиям `fragments-list-updated` / `elements-updated`).

**Грабля:** у мешей IFC-фрагментов That Open позиция хранится на GPU и **не имеет
CPU-массива** (`geometry.attributes.position.array === undefined`). Стандартный
three-mesh-bvh raycast на таких падает: `Cannot read properties of undefined (reading '0')`
в `Mesh._computeIntersections`. Поскольку OBC-рейкастер измерителя срабатывает на КАЖДЫЙ
pointermove — при загруженном IFC «Длина/Площадь/Сечение» молча перестают работать
(замер не создаётся вообще). Долго казалось, что инструменты «для красоты».

**Как правильно (сохранять):** в `rebuildWorldMeshes` добавлять меш в `world.meshes`
только если `geometry.attributes.position.array` существует. CAD-меши (воздуховоды/стены/
лотки — обычная CPU-геометрия) проходят и измеряются; IFC-фрагменты исключаются (по ним
стандартный raycast всё равно невозможен). Проверено: после фикса Length и Clipper
реально создают результат при загруженном IFC. Это та же природа, что §11.1.

## 12. Геометрия фасонных частей (как делать «красиво, как в Ревите»)

В `DuctDrawingTool.renderAll`, ветка `elem.type === "fitting"`:
- `dirAwayFromNode(duct)` — единичный вектор вдоль воздуховода, считая ОТ узла наружу
  (определяет, какой конец воздуховода в узле). Осторожно: использует `.sub()/.negate()`,
  которые мутируют — но векторы создаются свежими на каждый вызов, это ок.
- **Круглый отвод:** `createRoundElbow(node, dirA, dirB, radius)` — `TubeGeometry` по
  `QuadraticBezierCurve3` через точки `node±dir*off` с контролем в узле. Гладкий гиб.
  Геометрия строится в МИРОВЫХ координатах, меш стоит в `(0,0,0)`.
- **Прямоугольный отвод:** `createRectElbow` — гладкая ПРОТЯЖКА сечения `w×h` вручную
  (`BufferGeometry`) по дуге `QuadraticBezierCurve3` через `node±dir*off`. Сечение
  ориентируется ЯВНЫМ фреймом на каждом сегменте: `right = worldUp × tangent`,
  `up = tangent × right` (worldUp=(0,1,0)) — поэтому `w` всегда горизонтальна, `h`
  вертикальна. `off = max(max(w,h)*1.2, 0.15)` и ОБЯЗАН совпадать с укорачиванием в
  `getShortenedEndpoints` (иначе зазор/наезд на торцы каналов). Материал → `DoubleSide`.
  ⚠️ **Так сделано не от хорошей жизни:** ExtrudeGeometry/`TubeGeometry`/Frenet-фрейм
  крутят профиль (TBN перекатывается на дуге) и меняют местами `w↔h` — это чинилось
  тремя коммитами подряд. НЕ «упрощай» обратно к ExtrudeGeometry или «коробу по
  биссектрисе» — твист вернётся. То же относится к лоткам (`tray` зовёт тот же метод).
- **Переход «квадрат‑в‑круг»:** `createSquareToRound(node, axisToRound, w, h, d, length)` —
  кастомная `BufferGeometry`: два кольца по 32 сегмента (прямоугольный торец на `-Z/2`,
  круглый на `+Z/2`), соединённые квадами. Угловое соответствие точек: точка окружности
  под углом θ ↔ точка периметра прямоугольника в том же направлении θ. Локальная ось +Z
  выставляется на круглый воздуховод (`axisToRound`).
- **Конический переход (круг‑круг):** `CylinderGeometry(r2, r1, length, 24)` вдоль оси.
- **Тройник:** компактный коннектор (сфера для круга / короб для прямоугольника).

Если делаешь новую фасонную часть — строй геометрию здесь же и обязательно ставь
`mesh.userData = { elementId: elem.id }` (иначе элемент не выберется и не подсветится).

## 13. Спецификация (BOM)

- `BOMCalculator.calculate(elements)` группирует элементы: воздуховоды (по форме/размеру/

  Перед экспортом проект надо **сохранить** (кнопка в тулбаре).

## 14. UI‑слой BUI/lit — КРИТИЧЕСКИЕ ГРАБЛИ ⚠️

UI — это веб‑компоненты `@thatopen/ui` (`bim-panel-section`, `bim-button`,
`bim-dropdown`, `bim-number-input`, `bim-table`, `bim-tabs`, …) на базе lit.
Шаблоны — функции `StatefullComponent(state, update)`, рендерятся через `BUI.html\`...\``.
`update()` перезапускает шаблон.

### 14.1 ⚠️ Правило ОДНОГО корня (самая коварная грабля)
**Grid‑managed `StatefullComponent` (через `grid.elements = {...}`) ДОЛЖЕН возвращать
ОДИН и тот же корневой шаблон.** Если возвращать ДВА разных `BUI.html` по условию
(напр. «свойства» vs «дефолт»), то при `update()` lit подменяет корневой узел, а grid
держит ссылку на старый (узел проецируется через слот и отсоединяется) — шаблон
исполняется, но **в видимый DOM не попадает**. Именно из‑за этого панель свойств молча
показывала «Selection Data» вместо свойств.

**Правильно:** один корневой `<bim-panel-section>`, внутри условно меняются только
`label` и содержимое:
```ts
return BUI.html`
  <bim-panel-section label=${selected ? "Свойства элемента" : "Selection Data"}>
    ${selected ? propsContent : defaultContent}
  </bim-panel-section>`;
```
Альтернатива (как у спецификации): встроить панель как **standalone‑компонент‑ребёнок**
(`BUI.Component.create(...)` внутри `<bim-tabs>`/`<div>`), а не как корень grid‑элемента —
тогда `update()` коммитит нормально.

### 14.2 ⚠️ Уровни контраста темы (чёрное на чёрном)
В теме определены только `--bim-ui_bg-contrast-` **10, 20, 30, 40, 60, 80, 100**.
Уровни **0, 50, 70, 90 — ПУСТЫЕ**. `var(--bim-ui_bg-contrast-90)` без fallback → текст
становится **чёрным** (невидимым на тёмном фоне). Для текста бери `-100` (светлый),
`-80`/`-60` (серый). Это уже один раз сделало всю спецификацию нечитаемой.

### 14.3 Утечка слушателей
Шаблоны при каждом рендере вешают слушатели (`window.addEventListener`,
`highlighter.events.*.add(...)`). Старые снимаются по именованному ключу в `window`, но
`highlighter.events.*.add` накапливаются. Регистрируй «тяжёлые» подписки один раз
(через флаг) либо не добавляй их в теле шаблона повторно.

### 14.4 Раскладка
`grids/content.ts` задаёт сетку `models | viewer` сверху и `viewpoints(=вкладки
Спецификация/Видовые точки) | viewer` снизу. Левая узкая колонка — `groups/grid-sidebar.ts`.
Панель свойств (`elementData`) — **выезжающая справа панель (drawer)**, не колонка сетки:
абсолютно спозиционированный `<div>` поверх грида, появляется при выборе элемента
(`transform: translateX`), сам компонент свойств создаётся как singleton
(`window.__elementsDataPanelInstance`).

### 14.5 ⚠️ Корень `contentGridTemplate` ДОЛЖЕН быть `<bim-grid>` (или main.ts достаёт его сам)
`main.ts` делает `const [contentGrid] = BUI.Component.create(contentGridTemplate, …)` и
ожидает, что вернётся **сама `<bim-grid>`** — он обращается к `contentGrid.layouts`,
`contentGrid.layout`, `addEventListener("layoutchange")` и передаёт её в сайдбар
(`Object.keys(grid.layouts)`).

Если завернуть `<bim-grid>` в обёртку (`<div>` ради drawer/оверлея), корнем компонента
станет **div**, у него НЕТ `.layouts/.layout` → `Object.keys(grid.layouts)` бросает
`TypeError: undefined is not an object` → layout не применяется → **вьюпорт схлопывается
в 0×0** → лавина `WebGL: INVALID_FRAMEBUFFER_OPERATION: ... Attachment has zero size` и
чёрный экран. (WebGL‑ошибки тут — СЛЕДСТВИЕ, а не причина; ищи `grid.layouts`.)

**Как правильно при обёртке:** в `main.ts` доставать настоящую сетку изнутри —
`contentRoot.querySelector('#app-content')` (id = `CONTENT_GRID_ID`) с fallback на корень —
и использовать её для `layouts/layout/layoutchange/сайдбара`, а в app‑грид класть обёртку:
```ts
const [contentRoot] = BUI.Component.create(contentGridTemplate, {...});
const contentGrid = (contentRoot.querySelector(`#${CONTENT_GRID_ID}`) ?? contentRoot) as BUI.Grid<...>;
// ... setInitialLayout/sidebar используют contentGrid (внутреннюю сетку)
app.elements = { sidebar: {...}, contentGrid: contentRoot };  // в app кладём обёртку
```

## 15. Бэкенд API (FastAPI, `http://127.0.0.1:8000`)

CORS открыт (`*`). БД — SQLite `vent_mvp.db` (создаётся и сидируется при старте).

| Метод | Путь | Назначение |
|-------|------|-----------|
| GET | `/sortament?shape=round\|rectangular` | Справочник сечений (ВСН 353‑86) |
| POST | `/projects` | Создать проект (`{name, units?}`) → `{id (uuid), ...}` |
| GET | `/projects/{id}` | Получить проект (`graph.elements`) |
| PUT | `/projects/{id}` | Обновить (частично: `name/version/units/graph`) |
| GET | `/projects/{id}/export/xlsx` | Скачать Excel‑ведомость (StreamingResponse) |

- `Project`: `id` (uuid‑строка), `name`, `version`, `units` (по умолч. "mm"),
  `graph` (JSON `{elements: [...]}`), таймстемпы.
- `Sortament`: `ref` (PK), `shape`, `d`/`w`/`h`, `wall_thickness`, `mass_per_m`, `source`.
- Тулбар хранит текущий `project_id` в `localStorage["vent_mvp_project_id"]` и при
  первом действии создаёт проект автоматически (`ensureProjectExists`).
- **IFC‑экспорт — клиентский** (`IfcExporter.exportToIfc`, генерит текстовый IFC2x3 и
  скачивает `.ifc`), бэкенд в нём не участвует.

## 17. Чего НЕ делать (реальные грабли этого проекта)

1. **Не возвращай два разных `BUI.html` из grid‑панели** — см. §14.1. Панель «оживёт»
   в логах, но не в DOM.
2. **Не используй `--bim-ui_bg-contrast-90/70/50/0`** для цвета — будет невидимо (§14.2).
3. **Не обнуляй `selectedCustomElement` в `onClear`** панели свойств — затрёт выбор (§9).
4. **Не путай мм и метры.** Любая работа с координатами проходит через `/1000` или `*1000`.
5. **Не забывай `mesh.userData.elementId`** на новых мешах — иначе элемент не выбирается.
6. **Не запускай бэкенд из папки `server/`** напрямую — относительные импорты упадут;
   только `python3 -m server.main` из корня.
7. **Не правь фасонные части в графе вручную** — `FittingGenerator` их пересоздаёт.
8. **Не доверяй «выглядит правильно в коде»** для 3D/UI — проверяй в браузере.
9. **Не оборачивай `<bim-grid>` в обёртку, не починив `main.ts`** — корень
   `contentGridTemplate` должен остаться сеткой, иначе `grid.layouts` undefined →
   вьюпорт 0×0 → чёрный экран и WebGL `zero size` (§14.5).
10. **Не вызывай `Snapping.getIfcIntersection` безусловно на каждый mousemove и не
    рейкасть fragments «в лоб» через `intersectObjects`** — упадёт на мешах без
    `position`-атрибута и заморозит черчение у IFC. Снап к IFC — по `Alt`, рейкаст —
    per-mesh в `try/catch` (§11.1). Уже починено — не возвращай как было.
11. **Не клади IFC-фрагменты в `world.meshes`** (`rebuildWorldMeshes`) — у них GPU-геометрия
    без `position.array`, OBC-рейкастер измерений/сечения на них падает → Length/Area/Clipper
    перестают работать при загруженном IFC. Фильтруй по `position.array` (§11.2). Починено.
12. **Не делай прямоугольный отвод/лоток через `ExtrudeGeometry`/`TubeGeometry`/Frenet и не
    «по биссектрисе»** — профиль крутится, `w↔h` меняются местами. Только ручная протяжка с
    явным `worldUp`-фреймом, `off` синхронен `getShortenedEndpoints` (§12). Чинилось 3 коммита.
13. **Не меняй `DEVICE_PORTS`/локальные порты прибора в одном месте** — координаты портов
    дублируются (синхрон `ConnectionNodes` ↔ `SystemManager` ↔ `DuctDrawingTool` ↔ `TwoPipe`).
    Поменял в одном — поменяй везде, иначе подводки/системы разъедутся (§5.8).
14. **Connect-builders (`ConnectionNodes.*`) МУТИРУЮТ массив `elements` на месте** (режут трубы,
    удаляют старые подводки). После `connect(...)` ОБЯЗАТЕЛЬНО прогони
    `FittingGenerator.generateFittings` → подмени `projectElements` → `renderAll` →
    `elements-updated` (как в `main.ts`). Иначе узлы/спецификация/3D разойдутся.
15. **Не плоди третью копию connect-флоу** под кондеи/розетки — `radiator`/`terminal` уже два
    зеркальных блока в `main.ts`; новые дисциплины только через единый движок (§5.8 «Долг»,
    ТЗ §23 FR-PLACE-2). Это прямое требование заказчика «единая флоу логика».

## 17-bis. Инциденты «уронил всё» по СИМПТОМУ (диагностика с конца)

Когда что-то сломалось — ищи по тому, что ВИДИШЬ на экране, а не по тому, что менял.
Все эти случаи уже происходили и починены; не возвращай как было.

| Что видишь | Настоящая причина | Где |
|---|---|---|
| **Двери/окна/щиты/радиаторы исчезли** после добавления элемента | `FittingGenerator.generateFittings` не пробросил их тип (не тотальная функция) | §10 ⚠️ |
| **Чёрный экран + лавина WebGL `zero size`** | `<bim-grid>` завёрнут в `<div>` → `grid.layouts` undefined → вьюпорт 0×0 (WebGL — следствие!) | §14.5 |
| **Панель свойств показывает «Selection Data» вместо свойств** (в логах всё ок) | grid-панель вернула ДВА разных `BUI.html` → lit отсоединил корень от слота | §14.1 |
| **Текст чёрный на чёрном / спецификация нечитаема** | `--bim-ui_bg-contrast-90/70/50/0` — пустые → чёрный | §14.2 |
| **Измерения/сечение (Length/Area/Clipper) перестали работать при IFC** | IFC-фрагменты попали в `world.meshes`; рейкастер падает на GPU-геометрии без `position.array` | §11.2 |
| **Черчение «замерзает» рядом с IFC** | безусловный рейкаст fragments на mousemove падает | §11.1 |
| **У прямоугольного отвода/лотка перепутаны ширина/высота, профиль крутит** | `ExtrudeGeometry`/Frenet вместо ручной протяжки с `worldUp` | §12 ⚠️ |
| **Подводки/системы «разъехались» после правки портов** | `DEVICE_PORTS` поменян в одном из 4 мест | §17.13 |

Общий принцип под этот проект: **3D/UE-результат не виден в коде** — почти каждая поломка
тут «логика верная, но нарушена негласная конвенция движка». Поэтому правило §16: проверка
ТОЛЬКО в браузере, а не «выглядит правильно».
